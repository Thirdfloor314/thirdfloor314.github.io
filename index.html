01 Featured project

beatslides

Turns a folder of pictures into a slideshow that cuts on the beat of a song.

  • Python
  • NumPy
  • ffmpeg
  • Qt6
  • DSP

The hard part isn't the video, it's knowing where the beats are. I wrote the detection from scratch — no librosa, no cloud API, no model. Just a spectrogram, some signal processing and a dynamic program, in about 1 200 lines of Python driving ffmpeg.

How the beat detection works

  1. 01Decode to 22 kHz mono and take a 96-band mel spectrogram.
  2. 02Build an onset envelope from half-wave-rectified spectral flux, minus a local mean, so quiet passages still peak usefully.
  3. 03Estimate tempo by autocorrelation scored through a comb filter — each candidate lag scored by the sum of its integer multiples — with a log-normal prior at 120 BPM, refined by parabolic interpolation.
  4. 04Place beats with Ellis-style dynamic programming: maximise onset strength while penalising drift from the tempo period, then backtrace.
  5. 05Shift the grid by a quarter window, because spectral flux peaks slightly before the true transient.

Measured against a synthetic 120 BPM click track: 120.2 BPM detected, every beat within one 30 fps frame of the true grid.

It can also follow the song's structure

With --adaptive the pacing stops being constant and starts tracking the music: a DCT of each beat's spectrum gives a timbre fingerprint, a self-similarity matrix plus a sliding checkerboard novelty kernel finds the section boundaries, and sections that sound alike are grouped so a chorus keeps one pace every time it comes round.

Engineering decisions I'd defend

  • Verify the pixels, not the plan. Correctness checks decode the finished video and diff frames against the detected beat times. Several real bugs — a 35 ms flash, a wrong-octave tempo — were invisible to every other check.
  • Test across a library, not a track. Both of those bugs only appeared after sweeping a whole music folder.
  • Whole-frame timelines. Slide lengths are laid out in integer frames so rounding can't accumulate and drift off the beat over a four-minute song.
  • Flat memory at any length. Plain cuts go through ffmpeg's concat demuxer; mixed photo/video slides render per-segment and join without re-encoding, so a thousand slides costs the same RAM as ten.
  • Cut what doesn't measure. Onset density looked like a good second intensity signal and inverted the pacing on songs with busy verses, so it was deleted.

Ships as a CLI and a Qt6 desktop app whose live "plan" line is computed by the real layout code — you see the exact slide count and timing before rendering anything.

02 Other things I've built

HouseFountier live

A rental marketplace for Botswana — tenants find housing, landlords list it.

Running at housefountier.site. React and TypeScript on Vite, Tailwind with shadcn/ui, and Supabase for Postgres, auth and image storage. Browse and search listings, map them with Leaflet, create and edit your own, and hand off to the landlord over WhatsApp — a wa.me deep link, because that is how people actually make contact here.

The part worth pointing at is the data model: 21 migrations and row-level security policies written per role — what the public may read, what a landlord may touch on their own listings, what an admin may moderate. Access is enforced in Postgres rather than in the UI, so a forged request fails at the database. Contact inquiries and listing reports are separate tables feeding an admin dashboard, which is what "verified landlords" has to mean if it is going to mean anything.

  • React
  • TypeScript
  • Supabase
  • PostgreSQL
  • Tailwind
  • Leaflet

automix

An auto-DJ. Give it a folder, get one continuous beat-matched set.

Analyses every track for tempo, beat grid, downbeat phase, musical key and energy shape, then orders the set so keys agree (Camelot wheel), tempos are reachable and the energy arcs the way a set should. Each join is drawn from ten real DJ moves, steered by what the two tracks are doing — not a crossfade.

The detail that made it work: one rigid constant-tempo grid fitted per track. Per-beat tracking drifts and breaks beat-matching minutes later. Correctness is checked by re-analysing the rendered mix around each join and confirming the measured BPM matches the plan.

  • Python
  • NumPy
  • Electron
  • React
  • TypeScript

ErrandGo

Android marketplace for errands — post one, claim one, chat, rate.

Kotlin and Jetpack Compose on a live Firebase backend: email/password auth, Firestore in the Johannesburg region, and access rules kept in the repo and deployed from the CLI rather than clicked into a console.

Full loop across ~33 Kotlin sources — posting and claiming errands, in-app chat, profiles and ratings — with the data model and access rules designed together instead of after.

  • Kotlin
  • Jetpack Compose
  • Firebase Auth
  • Firestore
  • Gradle

Multi-Out

Play audio on several outputs at once, and follow Bluetooth automatically.

Built on PipeWire's combine-stream: tick the outputs that should play and they share one virtual sink, with optional latency compensation for devices that drift.

Switching never drops the music. The new sink is created and linked first, live streams are migrated onto it, and only then is the old one torn down — so a Bluetooth headset stays connected through the change. Ships with installers and a systemd unit for auto-switching.

  • Python
  • PipeWire
  • systemd
  • Linux audio

Holo port

Acoustic tap zones — turn a plain desk into an input surface.

A Fedora/Linux port of JustinGamer191/Holo: it listens through the microphone and classifies where on the desk you tapped, mapping zones to actions. Packaged properly as a pyproject install with a CLI, a GTK front end and a test suite.

  • Python
  • sounddevice
  • PyGObject
  • NumPy

Supabase migrator

Moving a live Postgres/Supabase database between projects without losing rows.

Node scripts that introspect the source schema, generate ordered SQL that respects foreign keys, restore into the destination and then verify the destination actually matches — because a migration you haven't checked row-for-row isn't finished.

03 How I work

I code with AI agents.

Claude Code in a terminal, most days, on most of the work on this page. I'd rather say that plainly than have you guess. It hasn't made the engineering easier — it has moved where the engineering is.

  • Drafts got cheap. Knowing what to ask for didn't.

    An agent will happily build the wrong thing quickly. The work that decides whether a project is any good — what it should do, what the real constraint is, which design survives contact with a whole music library — is still mine to do.

  • I decide how a change gets proven.

    Every claim on this page is measured, not asserted: a beat grid checked against decoded frames, a mix re-analysed at each join to confirm the rendered BPM matches the plan. An agent can write that harness. Insisting the harness exists, and believing its answer over a confident explanation, is the job.

  • Nothing ships that I haven't read.

    I review the diff and I delete what doesn't earn its place — a vocal detector that measured a −0.0007 effect on full tracks, an intensity signal that inverted the pacing on busy verses. Both were working code. Both are gone.
